# PM Pixel Simulator 下一阶段 Codex 迭代指令

本文档用于下一轮 Codex 开发。目标不是重做 MVP，而是在已经跑通的基础上，把“历史案例核查推演质量、案例库结构化、复制到工作”做成可验证的小迭代。

## 关键假设

1. 当前版本已经能启动游戏、调用 OpenAI-Compatible 接口、保存历史案例、打开历史详情、导出单个案例。
2. `storage/simulation-records.json` 是本地真实案例库，可能包含敏感项目内容，不能提交、不能在答复里展开案例原文。
3. “全部历史案例保存”和“导出某个案例”是两个不同能力：保存用于长期案例库，导出用于分享或素材沉淀。
4. 下一阶段仍保持本地文件型 MVP，不引入登录、数据库、云同步、多用户权限或复杂后台。

## 当前结构核查摘要

本次只做结构核查，不复述真实案例内容：

- 当前历史案例数：3 个。
- 推演来源：3 个均为 `live_llm`。
- 项目阶段覆盖：`planning`、`feasibility`、`acceptance`。
- 核心结果字段完整：角色推演、漏洞扫描、能力评分、行动方案、案例沉淀均存在。
- 平均每案角色结果约 4.33 个，漏洞扫描约 5.33 项，当日行动约 3.33 项。
- 每个案例都有 `shareableOutputs`，但模型结果里没有稳定产出“可复用模板包”；目前主要依赖前端兜底逻辑补齐模板包。
- `caseType` 存在不统一现象，既有中文类型，也出现阶段值，例如 `planning`，说明案例库结构化需要补强。

## 总体迭代目标

把 PM Pixel Simulator 从“能生成和保存案例”推进到“能积累、筛选、复盘、复制到实际工作”的训练工具。

成功标准：

- 能看出每个历史案例的推演质量是否合格。
- 案例库可以按稳定字段归类，而不是只靠全文搜索。
- 用户能从一个案例里复制可直接用于工作的材料，而不是只导出整份 Markdown。
- 本地规则和大模型接口都保持可用。
- 旧历史案例不丢失，旧字段能兼容读取。

## 第一阶段：历史案例质量核查

### 目标

给每个历史案例增加一个可计算的质量核查结果，用来判断大模型推演是否真的有训练价值。

### 建议改动

1. 新增 `src/services/caseQualityService.ts`。
2. 新增 `CaseQualityReport` 类型，字段建议包含：
   - `overallStatus`: `pass | warning | fail`
   - `score`: 0 到 100
   - `checks`: 每个检查项的结果
   - `warnings`: 需要人工复核的问题
3. 核查项至少包含：
   - 角色视角是否明显区分。
   - 行动方案是否包含责任人、动作、时间、成果、检查人。
   - 漏洞扫描是否覆盖目标、责任、节点、成果、风险、闭环、留痕。
   - 能力评分是否有扣分原因和训练重点。
   - 案例沉淀是否有案例类型、暴露问题、可复用模板、可复制成果。
   - 是否出现空泛表达，例如“加强沟通”“持续跟进”但没有具体输出。
4. 在历史详情页增加“推演质量核查”区域。
5. 在历史列表卡片上显示一个轻量状态：合格 / 需复核 / 不完整。

### 验收标准

- 旧案例能打开并显示核查状态。
- 缺少关键字段的案例不会导致页面报错。
- 至少用现有 3 个历史案例验证，不能在提交信息或答复里泄露案例正文。
- 核查规则先用确定性代码实现，不调用大模型。

## 第二阶段：案例库结构化

### 目标

让案例库不只是一堆历史记录，而是可以按项目阶段、问题类型、能力短板、可复用材料进行管理。

### 建议改动

1. 扩展类型时保持可选字段，兼容旧案例。
2. 建议新增 `caseAsset.libraryMeta`，字段如下：
   - `normalizedCaseType`: 规范化案例类型。
   - `problemTags`: 问题标签，例如责任不清、节点失控、成果不明、风险未识别、留痕不足。
   - `abilityTags`: 能力短板标签，例如全局视野、节点控制、责任判断、协同推进、闭环能力。
   - `materialTags`: 可沉淀材料标签，例如会议纪要、责任节点表、催办记录、报审清单、归档清单。
   - `trainingValue`: `high | medium | low`
   - `contentValue`: `high | medium | low`
3. 增加规范化函数，例如 `normalizeCaseLibraryMeta(record)`。
4. 历史列表增加标签展示和筛选，优先做：
   - 问题类型筛选。
   - 能力短板筛选。
   - 是否适合培训筛选。
5. 不要一次性重写 `storage/simulation-records.json`。读取时动态补齐即可；需要持久化时再单独设计迁移按钮或脚本。

### 验收标准

- 现有历史案例无需迁移即可显示结构化标签。
- `caseType` 出现英文阶段值时，可以映射为更合理的中文案例类型或标记为“待归类”。
- 筛选后计数正确，清空筛选可恢复全部案例。

## 第三阶段：“复制到工作”能力

### 目标

把“可直接分享成果”升级为“复制到工作”，让用户能按工作场景复制单项材料。

### 建议改动

1. 保留现有“导出 Markdown”作为单个案例分享能力。
2. 在历史详情页的案例沉淀区新增“复制到工作”分组。
3. 将可复制材料拆成稳定类型，不只依赖标题文本：
   - `meeting_notice`: 专题会通知
   - `meeting_minutes`: 专题会议纪要
   - `responsibility_table`: 责任节点表
   - `reminder_record`: 催办记录
   - `reporting_brief`: 上报口径
   - `archive_checklist`: 资料归档清单
   - `review_checklist`: 报审附件核对表
4. 扩展 `ShareableCaseOutput` 时保持兼容：
   - 新增可选 `outputType`。
   - 新增可选 `copyLabel`。
   - 新增可选 `workScenario`。
5. 修改 `caseAssetService.ts`，由它统一生成旧案例的兜底工作材料。
6. 每个材料都提供独立复制按钮，复制成功后显示短暂状态。

### 验收标准

- 用户可以只复制“专题会议纪要”，不必导出整份案例。
- 用户可以只复制“责任节点表”或“资料归档清单”。
- 旧案例没有 `outputType` 时仍能通过兜底规则生成材料。
- 导出 Markdown 中仍包含完整分享成果，不被“复制到工作”替代。

## 第四阶段：提示词与大模型输出约束

### 目标

减少大模型输出不稳定，确保新案例天然带有结构化标签和工作材料。

### 建议改动

1. 更新 `src/services/promptTemplate.ts`。
2. 要求模型输出 `caseAsset.libraryMeta`。
3. 要求 `shareableOutputs` 每项尽量带 `outputType`。
4. 明确禁止只写泛泛建议，要求材料可直接复制到真实工作。
5. 在接口解析处保持宽容：模型缺字段时，用本地兜底函数补齐，不让页面崩溃。

### 验收标准

- 新生成案例更容易形成统一标签。
- 新生成案例至少有 5 类可复制工作材料。
- 模型缺失结构化字段时，历史详情仍可正常展示。

## 第五阶段：案例库管理增强

### 目标

补齐轻量管理能力，但不做复杂后台。

### 建议改动

1. 历史列表增加批量视角：
   - 全部案例数。
   - 高训练价值案例数。
   - 需复核案例数。
   - 可复制工作材料覆盖数。
2. 增加“案例复核状态”：
   - `unreviewed`: 未复核
   - `approved`: 已确认可作为训练案例
   - `needs_edit`: 需要人工修改
3. 复核状态可以先只保存在记录里，不做复杂审批。
4. 删除按钮保持谨慎，后续可考虑二次确认。

### 验收标准

- 用户能知道哪些案例可以直接用于培训，哪些还需要改。
- 复核状态不影响旧案例读取。
- 不引入登录、权限、数据库。

## 推荐执行顺序

1. 先做第一阶段：质量核查。
2. 再做第二阶段：结构化标签。
3. 再做第三阶段：复制到工作。
4. 最后调整提示词，让新生成案例自动适配新结构。

不要同时做所有阶段。每轮 Codex 只做一个阶段，避免破坏已跑通的核心流程。

```bash

```

```bash
npm run dev -- --hostname 127.0.0.1 --port 3000
```

需要验证的页面：

- 首页创建推演。
- 历史案例列表。
- 历史案例详情。
- 导出 Markdown。
